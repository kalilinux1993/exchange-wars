# Findings

## Phase 13x — Rest Heal-ETA (2026-06-12)

188. **A cost the engine imposes but the UI never names is a hidden tax on the player's decision — the wounds-mend-slowly rule existed in sim.ts for bricks, invisible until you put a number on it.** Wounds carry between dives and heal only out of the field at +1 hp per 3 ticks — a real constraint on how often you can dive — yet the UI showed only a static hp bar, so "rest first or embark hurt?" was decided blind. Naming the cost ("≈N ticks to heal") turns an invisible rule into a planned action. Lessons: (1) surface the ETA/cost of every engine rule the player must plan around — a mechanic the player can't SEE the cost of is one they'll mis-plan, and the fix is arithmetic the UI can do from constants it already has. (2) Gate the readout on the exact conditions the rule fires (`hp !== undefined` = wounded, `!expedition` = out of field) so it never lies — showing a heal ETA mid-dive (where regen is paused) would be worse than showing nothing. (3) Mirror the engine's formula exactly (`+1 / regenTicks`) rather than approximating, and source `REST_REGEN_TICKS` from the engine so the ETA tracks the rule if it's ever retuned — the same single-source discipline as the tax in #185. Completes the dive-decision triad: embark forecast (full hp) → mid-dive push read (13p, current hp) → rest ETA (13x, between dives). UI-only, no engine change → no verify-score redeploy. Brick 154.

## Phase 13w — Skill-Cell Level-Up Flash (2026-06-12)

187. **Notify-and-confirm is two surfaces for one event — the toast says WHAT happened, the flash says WHERE, and a player believes the second more than the first.** 13v's toast announces "Attack up!"; 13w pops the Attack cell gold. Neither alone is as good as both: a toast is transient and can be missed or overridden (it's a single shared slot), while a flash on the actual skill is durable for its 1.2s and unambiguous about which stat moved. Placing the flash on the Adventure tab — where combat (and thus xp gain) happens — means it fires in the player's field of view, not on a panel they'd have to switch to. Lessons: (1) for an important event, pair an ephemeral global notification with a persistent local highlight on the thing that changed; the redundancy is the point, not waste. (2) Share the detection (`leveledUp`) between the toast and the flash so they can never disagree about what leveled — the same anti-divergence discipline as the gear tie-break (#182), applied to feedback rather than logic. (3) The lazy-init-baseline guard recurs a third time (#161, #186): any "celebrate a change" effect needs "first observation sets the baseline silently," or mounting the component re-fires every latent level. UI-only, no engine change → no verify-score redeploy. Brick 153.

## Phase 13v — Combat Level-Up Celebration (2026-06-12)

186. **The most basic feedback is the easiest to forget to build — the game celebrated deeds and daily records but never the thing an RPG is fundamentally about: leveling up.** Across 150+ bricks the progression loop had milestones, daily-record celebrations, and a live xp-to-next bar, yet the moment a skill actually ticked over fired nothing. It's the kind of gap that hides precisely because it's obvious: everyone assumes it's there. The fix reused the exact diff-detection-into-toast pattern already proven by death-capture and the daily-record (#161): a lazy-init ref of prior levels, checked in the same `refreshProgress` that runs after every command/tick/fast-forward. Lessons: (1) audit the CORE loop's feedback explicitly — the fancy celebrations (records, deeds) can all exist while the foundational one is missing, because attention flows to the novel, not the obvious. (2) Toast PRIORITY is a real design decision encoded by call ORDER on a single last-writer-wins slot: level-up fires before the milestone check so a deed earned the same tick outranks it — and the render test surfaced this by accident (a level-15 jump crossed a combat-level deed that ate the toast), which is exactly the override behaviour intended, so the test was tightened to a deed-free 1→2 jump rather than the priority "fixed". (3) Lazy null-init of the comparison ref is the recurring guard (#161, feed-glow): "first observation establishes the baseline, never celebrates it" is what stops a save-load from phantom-firing every latent level at once. UI-only, no engine change → no verify-score redeploy. Brick 152.

## Phase 13u — Recent Flips (per-round-trip journal) (2026-06-12)

185. **The book that aggregates can't un-aggregate — to show per-flip detail you re-run the FIFO and keep what the book throws away, rather than trying to recover it from the totals.** The lifetime tradeBook folds every sell into per-item `{profit, soldUnits}` aggregates (applyFillToBook), so the individual round-trips are gone the moment they're booked — you can't reconstruct "this specific Shark flip made +470" from the totals. The clean answer isn't new persisted state; it's a SECOND pass over the same fills with the same FIFO+tax arithmetic that keeps per-flip records instead of summing them. Lessons: (1) when a feature needs detail an existing aggregator discards, re-derive from the raw events with a parallel computation rather than enriching the aggregator (which would bloat the hot path and the saved state for a display concern) — the fills window is right there. (2) Parallel FIFO must match the book's tax/rounding EXACTLY (`price − floor(price·tax)` per unit) or the per-flip profits won't reconcile with the per-item realized totals — reusing the same formula, not re-deriving it, is what keeps "flips" and "Profit by Item" telling the same story. (3) A new MODE on an existing component (TradeFeed tape/mine/flips) beats a new panel when it shares the data source — tape=all trades, mine=raw fills, flips=matched round-trips are three lenses on one window, not three panels competing for screen. Honest scope note logged: the window is capped at 50, so "recent" is literal; full history would need a persisted log (engine/save change), which the rolling window deliberately avoids. UI-only, no engine change → no verify-score redeploy. Brick 151.

## Phase 13t — GE-Capped Flip Marker (review-driven) (2026-06-12)

184. **A SOUND review still pays — its one latent note became a real feature, because "this flag is loose but never rendered" is an invitation to render it correctly.** An adversarial pass over the session's four money helpers found no bugs (good — the math was right), but flagged `flipAffordability.limited` as semantically loose: it could read `true` for a zero buy limit (units 0), saved only by the caller never surfacing it outside the affordable branch. The lazy response is "latent, ignore it." The better one: tighten the flag (`units >= 1`) so it's correct unconditionally, THEN surface it — a "GE" tag on flips you can afford but the buy limit caps, which is a genuine scaling signal (you can't do more this window even with more gp). Lessons: (1) a latent-but-wrong flag is debt that the next person who renders it will trip on; fixing it when you find it (not when it breaks) is cheap insurance, and pairing the fix with a use makes the correctness load-bearing instead of theoretical. (2) "no bugs found" is the GOAL of a review, not a failure of it — confidence that the money helpers are correct is itself the deliverable, and the small hardening is a bonus. (3) The distinction the marker draws (gp-bound ×N vs limit-bound ×N-GE vs unaffordable ✕) completes the affordability lens with the one piece of information a capital-rich player actually needs: "more gp won't help here." UI-only, no engine change → no verify-score redeploy. Brick 150.

## Phase 13s — Upgrade Affordability Hints (2026-06-12)

183. **A disabled button is a dead end; a disabled button with a distance is a goal — "5,000 gp (greyed out)" says no, "need +4,900" says not yet, keep flipping.** The shop greyed out upgrades you couldn't afford, which communicates the constraint but kills the motivation: the player learns they can't buy, not how to get there. Adding the shortfall turns each locked upgrade into a concrete saving target, and the spendable-purse header lets them compare at a glance. Same affordability lens as 13l (flips) and 13n (positions), now on the progression spend. Lessons: (1) when you block an action, show the GAP to unblocking it — a constraint with a distance is a quest; a constraint without one is a wall. (2) Show the RIGHT number for the decision: the shop header shows spendable gp (cash), not net worth, because upgrades can't be bought with held goods — putting net worth here would mislead (you'd think you could afford something you can't), so it's not a WealthPanel duplicate but a different, decision-correct figure. (3) One `need()` helper across four buttons keeps the four affordability hints identical by construction — the anti-divergence discipline (13r) applied preemptively, not retroactively. UI-only, no engine change → no verify-score redeploy. Brick 149.

## Phase 13r — Gear Tie-Break Consistency (review-driven) (2026-06-12)

182. **The adversarial review earned its keep on the comment, not the code — a tie-break divergence that's harmless in stats was paired with a comment that CONFIDENTLY lied about it, and the lie is the part that bites later.** After 13 un-reviewed feature bricks I pointed an adversarial review at the three independent "best gear per slot" pickers. It found exactly one real flaw: `deriveStats`, `equipBest`, and `equipped()` break ties by three different iteration orders, and the GEAR table has stat-identical ties — so the equip-best result can name a different itemId than the paperdoll preview. Blast radius is near-zero (tied pieces are stat-identical → combat, worth, and the golden sim hash are all invariant), but `equipBest`'s comment asserted "identical tie-break to deriveStats," which is false and would mislead the next person who trusts it. Lessons: (1) review yields most where there are MULTIPLE implementations of one concept — three pickers is three chances to diverge, and "they obviously agree" is exactly the assumption worth attacking. (2) A confident-but-wrong comment is a worse defect than the subtle behavioural divergence it describes, because the code can be re-derived but the comment is believed; fixing the lie mattered more than the itemId. (3) The fix made the rule ORDER-INDEPENDENT (explicit smaller-itemId tie-break) rather than "make everyone iterate the same collection" — encoding the invariant in the comparator beats encoding it in a fragile convention every call site must remember. (4) Left `deriveStats` untouched on purpose: its tie-break is unobservable (returns stats, ties are stat-identical), so changing ground-truth combat code for zero behavioural gain would be churn — the discipline is to fix what's observable, not everything the review touched. The review confirmed the other four claims (conservation, determinism, fallback, invariant counting) SOUND. Replay-affecting (equipBest item choice) → engine.js rebuilt, joins the redeploy batch; sim byte-identical. Brick 148.

## Phase 13q — Below-Break-Even Sell Tint (2026-06-12)

181. **A warning's effectiveness is set by its DISTANCE from the action it guards — the break-even readout existed below the field for bricks, but moving the same signal onto the input is what makes it catch the mistake.** The ticket already showed "break-even ≥ X · below break-even"; the data was right there. But it sat under the price field, so you'd type a loss-making price and only notice if you scanned down. Tinting the input itself puts the warning where the decision is entered — zero scan distance. Lessons: (1) co-locate the guard with the gesture: a validation rendered next to the control fires later (or never) than the same validation rendered ON the control; for loss-prevention, on-control wins. (2) This is the same "put it on the action" thread as 13o (payoff on the extract button) and 13i (delta on the buy ticket) — three bricks, one principle: information attached to the control beats information attached to a nearby readout. (3) Reusing the existing pure helper (`breakEvenSell`) meant the input tint and the readout can never disagree about what "below break-even" means — one source, two surfaces. Honest framing: it's advisory (the engine stays the rejection authority), tinting only what the math can prove is a post-tax loss vs your average cost. UI-only, no engine change → no verify-score redeploy. Brick 147.

## Phase 13p — Mid-Dive Push Read (2026-06-12)

180. **A forecast computed once at the start goes stale exactly when the stakes peak — the embark read was at full hp, but the dangerous decision is always made wounded, deep, with loot on the line.** The embark screen forecasts the region at full hp; that's the safe moment. The decision that actually matters — push deeper or bank — happens mid-dive after you've taken damage, and there the UI offered only a blind "venture deeper" button. The same `combatForecast` re-run at CURRENT hp turns a one-time pre-flight check into a live risk read that sharpens precisely as it gets dangerous. Lessons: (1) a decision aid must be evaluated at the moment of the decision, not the moment of setup — a static forecast is a different (weaker) feature than a live one, even with identical math, because hp moved. (2) Two halves of one decision belong together: 13o put the LOOT stake on the extract button, 13p puts the RISK read beside it, and the "— bank your haul?" nudge only fires when both conditions meet (risky AND loot held) — composing the two readouts into a single recommendation neither could give alone. (3) Reusing the engine-mirroring forecast (with the same dragonfire bonus the live combat read uses) keeps the embark, mid-dive, and in-combat reads consistent — one formula, three moments, no drift. UI-only, no engine change → no verify-score redeploy. Brick 146.

## Phase 13o — Extract Payoff on the Action (2026-06-12)

179. **Put the consequence on the verb — a button labelled with its payoff ("bank 5,000 gp") drives a decision that the same number sitting in a stats line never will.** The dive already showed loot as a neutral stat and offered a generic "extract (keep everything)" button. Both facts were present; the DECISION (lock in the haul vs push and risk it) wasn't framed where it's made. Moving the at-risk amount onto the action — "extract · bank N gp", green — turns a label into a prompt, the same move as 13i (gear delta on the buy ticket) and 13h↔13i (the same datum belongs at every point the decision is taken). Lessons: (1) status and action are different surfaces: a number in a readout answers "what is true", a number on a button answers "what happens if I press this" — push-your-luck games live or die on the second. (2) Showing the same value in two framings isn't the duplication the #169/#170/#173 discipline warns against — that rule is about COMPETING displays that can disagree; a value can't contradict itself, so status-vs-action framing is complementary, not redundant. (3) Rotating to the least-touched surface (the active dive) found a high-leverage one-line change precisely because it had had no attention — breadth-first rotation surfaces cheap wins that depth-first mining misses. UI-only, no engine change → no verify-score redeploy. Brick 145.

## Phase 13n — Underwater Positions Glance (2026-06-12)

178. **"Coloured red" is not "surfaced" — the loss was already visible per-row and still invisible in practice, because best-first sorting buried it below the fold.** PositionsPanel had tinted each position's paper P&L green/red since 12c, so one might call underwater-visibility "done." But the list sorts best-first and caps at 8, so the bleeding positions are exactly the ones that scroll off — the data was present and the signal was absent. The fix isn't more colour on the row, it's an AGGREGATE that doesn't depend on scroll position ("⚠ N underwater −X paper") plus a row tint strong enough to spot when a loser does appear. Lessons: (1) per-item styling and at-a-glance risk are different jobs — a property rendered on every row still fails if the rows you care about are the ones sorted away; surface the summary separately from the list. (2) Respect the data's honesty: only MARKED positions (those with a live price) count as underwater — an unmarked position has unknown P&L, not a loss, and conflating them would cry wolf. (3) This completed the trading RISK lens (holdings) as the counterpart to 13k/13l's ACQUISITION lens (what to buy) — the same system seen from "how am I doing?" vs "what do I do next?", and a cockpit needs both. UI-only, no engine change → no verify-score redeploy. Brick 144.

## Phase 13m — One-Tap "Prep Me" (2026-06-12)

177. **A "do everything" button is a dedupe problem wearing an automation costume — the work isn't applying the fixes, it's knowing that two warnings can share one fix.** 12q gave each embark warning its own "+pack" chip; the obvious "prep me" is just a loop over those chips. But the antifire and food warnings can resolve to the SAME item (super-antifire heals AND blocks breath), so a naive loop would pack two when one suffices, and worse, the button would offer itself for a single underlying fix that already has a chip. Deduping the fix items (`new Set`) and gating on `≥2 distinct` is what makes the button honest: it appears only when it genuinely saves taps, and packs exactly what's needed. Lessons: (1) a batch action over N items isn't N× the single action — the interesting logic is the cross-item relationships (shared fixes, conflicts, ordering) that don't exist at N=1. (2) Reuse the per-item resolver (`fixFor`) rather than re-deriving the fixes — the batch and the singles can never disagree about what clears a warning, the same discipline as #170's "reuse the consumer's own selection logic." (3) Pivoting systems for breadth paid the methodology dividend NEXT_STEPS predicted: after eight trading/equipment bricks, a 20-minute RPG-side brick closed a queued follow-up and kept the surface evenly developed. The test also pinned an emergent fact (dragons_maw reads "risky" for a fresh fighter, so the food warning fires) — a render test doubling as a forecast-calibration guard. UI-only, no engine change → no verify-score redeploy. Brick 143.

## Phase 13l — Flip Affordability Lens (2026-06-12)

176. **The honest version of a previously-DECLINED feature is often a different, shippable feature — "realizable profit" was rightly refused (needs order-flow depth the UI can't see), but "affordability" is the same intuition stripped to what the data CAN prove.** NEXT_STEPS recorded a deliberate decline: don't rank flips by realizable profit, because you can't know how much rests at the bid/ask. The temptation is to treat the whole area as off-limits. But the player's real question — "which of these can I actually act on right now?" — splits into a knowable part (gp/buy, capped by the GE buy limit = how many you can OPEN) and an unknowable part (how many will FILL = depth). `flipAffordability` answers only the knowable part, and the framing is everything: a `×N` badge labelled "units your gp can buy now", never "profit you'll make". Lessons: (1) when a feature is declined for an epistemic reason (the data can't support the claim), look for the adjacent claim the data DOES support — often 80% of the value survives once you drop the part you can't honestly assert. (2) Make the scope visible in the words: "fits purse" and "×N units" promise capital-coverage, not fills, so the UI never over-claims. (3) A filter that re-ranks deeper before slicing (limit 100 → filter affordable → take 4) surfaces the best AFFORDABLE option without abandoning the margin order — the constraint (your gp) is applied as a filter on an honest ranking, not baked into a fabricated score. UI-only, no engine change → no verify-score redeploy. Brick 142.

## Phase 13k — Return on Stake (2026-06-12)

175. **A cockpit can be richly instrumented and still miss the simplest question — six analytics panels measured spreads and positions, but none answered "am I up?"; the most-glanced number was the one not shown.** Branching off the equipment arc to the trading side, an Explore map found TopFlips/Movers/Depth/ProfitPanel/PositionsPanel all present — sophisticated decision aids — yet no single readout for net worth vs where you began. The Fortune chart plots worth over time but not the delta against the stake; realized/unrealized P&L is per-item, never a headline. The fix was one pure helper over a value (`game.startGp`) that already existed for exactly this purpose (it gates the double-your-stake deed) but was never surfaced as a number. Lessons: (1) audit for the OBVIOUS missing glance, not just sophisticated gaps — the more advanced the instrumentation, the easier it is to skip the trivial top-line everyone actually checks first. (2) When a baseline value already exists in the model (startGp), prefer surfacing it to inventing a new one — but VERIFY its real semantics first: I almost shipped this as "session P&L" until the grep showed startGp is HUMAN_START_GP preserved across reloads, i.e. lifetime, not session; labelling it honestly (lifetime vs stake) avoided a number that lies about its own scope. (3) Integrate into the panel that already owns the concept (WealthPanel) rather than adding a competing card — the #169/#170 anti-duplication discipline applies to additive features too, not just bug fixes. UI-only, no engine change → no verify-score redeploy. Brick 141.

## Phase 13j — Gear Findability on the Market (2026-06-12)

174. **A buy-decision aid is worthless if the player can't reach the buy — six bricks made gear safe, equippable, previewable, and priced, but gear was still un-findable among 128 commodities, so the whole arc hinged on a marker I hadn't built.** 13d–13i is a complete buy/equip/compare pipeline, yet every step assumed the player had already SELECTED a gear item. Acquisition is on the ordinary order book, and the market table's only categorisation (all/staples/exotics) splits by volatility — useless for finding the ~19 equippable items. So the arc had a hole at its very entrance: you can preview "+35 Attack before you buy" (13i) only once you've found the gear, and nothing helped you find it. The fix is small (a `gear` track + a per-row ⚔/🛡 marker) but it's the keystone — without it the upstream work is reachable only by knowing item names in advance. Lessons: (1) trace a feature arc from the user's FIRST action, not the one you happened to build last — the entrance (find the gear) is as load-bearing as the exit (equip it), and it's easy to polish the exit while the entrance stays locked. (2) Markers earn double duty: the ⚔/🛡 glyph both identifies gear and, via its title, answers "what level does it need?" — one affordance, two questions. (3) Reuse the discriminator the domain already has (`GEAR[id]`) rather than inventing a category flag on items — the engine's gear map IS the gear taxonomy, so the UI filter and the equip logic can never disagree about what "gear" means. UI-only, no engine change → no verify-score redeploy. Brick 140.

## Phase 13i — Pre-Buy Gear Delta (2026-06-12)

173. **A decision readout belongs wherever the decision is MADE, and the same decision is often made in two places — the satchel (13h) answers "should I equip this?", the trade ticket answers "should I buy this?", and they want the same number in both.** 13h surfaced the upgrade delta on owned gear, but an Explore pass confirmed gear is acquired on the ordinary order book (gear pieces are just tradeable catalog items — no special shop), so the BUY decision lives at the trade ticket, one step earlier than equipping. Putting the same `gearDelta` there means the player sees "+35 Attack over your Adamant dart" before committing gp, not only after the piece is sitting unequipped in the satchel. The reuse was nearly free because the helper was already pure and decoupled — the only friction was data: PlayerView deliberately omits combat levels, so the levels had to be threaded from App as a prop (made optional so isolated render tests don't need to fake an agent; absent levels just drops the "needs Atk N" note, never the delta). Lessons: (1) when you add a decision aid, ask "where ELSE is this same decision made?" — the buy and the equip are the same upgrade judgment at two moments, and covering only one leaves the gap where the gp is actually spent. (2) A pure helper with a small, explicit signature (id, worn, lvls) pays off precisely here — it dropped into a second component with no refactor, which a helper that read component state or context could not have. (3) Keep an optional prop's ABSENCE graceful (skip the level-gated note, keep the core readout) so the component stays testable in isolation without constructing the whole world. UI-only, no engine change → no verify-score redeploy. Brick 139.

## Phase 13h — Gear Upgrade Delta (2026-06-12)

172. **Close the loop back to the user's ORIGINAL words — five bricks of equipment plumbing (safe/equip/auto-equip/coherent display) all served a complaint that began "I'm trying to buy upgrade gear," and the buy DECISION was still the one thing left blind.** 13d–13g made gear safe from the clerk, equippable, one-click auto-equippable, and made the character sheet tell the truth. But the satchel still showed only an "equip" chip — nothing told you whether a piece you just bought actually BEATS what you wear. The decision the user actually described (is this an upgrade worth buying/equipping?) had no readout. `gearDelta` adds it: the governing-stat change vs the worn piece (weapon→Attack, armor→Defence), green for upgrade, red for downgrade, 🔒 when under-level, "no gain" for a sidegrade. Lessons: (1) when a feature arc grows long, re-read the user's FIRST sentence — the plumbing is necessary but the payoff is the specific decision they named, and it's easy to build everything around it without ever building it. (2) A read-only `WorldState` access is the right tool when the view projection lacks what display needs (combat levels aren't in `PlayerView`) — the UI rule forbids MUTATING outside applyCommand, not reading for display, so threading levels from `game` beats bloating the engine's view contract for a cosmetic. (3) Reuse the codebase's established colour semantics (`.up`=green/good, `.down`=red/bad, already set by the danger readout) so a new badge reads correctly on first sight without inventing a palette. UI-only (pure `gearDelta` helper + a badge), no engine change → no verify-score redeploy. Brick 138.

## Phase 13g — Paperdoll ↔ Worn Coherence (2026-06-12)

171. **Adding a new source of truth (persistent `worn`) silently invalidates every OLD display that derived the same concept a different way — the bug isn't in the new feature, it's in the stale readers you forgot were computing the answer themselves.** 13e/13f gave the player real persistent equipment (`worn`), and both new surfaces (PlayerPanel's "Equipped" list, the combat math) read it. But the Adventure-tab character sheet predated persistent equipment and still computed its paperdoll from `equipped(inventory, lvls)` — "best gear you could pack" — a PREVIEW that made sense only when packing was the only way to wear gear. Once equipping MOVES gear out of inventory into `worn`, that preview reads the wrong bucket: equip your best weapon and the figure shows the weapon slot DOWNGRADED (next-best still in the satchel) or empty, the instant you equipped your best. Same root for the "in battle: ⚔X 🛡Y" line, which called `deriveStats` without the `worn` arg and so ignored everything equipped. The Explore-agent map made the duplication explicit: two "equipment" displays in two tabs, derived two ways, free to disagree. Three durable lessons: (1) when you introduce a canonical store for a concept, GREP for every place that re-derives that concept and point them at the store — a derived preview is correct only until a real source exists, then it's a liar. (2) The fix needs no new plumbing when the component already holds the source — CharacterPanel already received the whole `agent`, so `agent.worn` was in hand; the work was realizing the read was stale, not wiring data. (3) Truthful beats flattering: if the player equipped a WORSE piece than they hold, the figure now shows the worse piece, because that's what fights — and `equipBest`/equip one-click the fix; a display that flatters ("you'd wield the dragon") while combat uses the adamant dart is worse than an honest downgrade. Mirrored `deriveStats`'s exact override rule so the figure, the effective stats, and the combat all agree by construction. UI-only (CharacterPanel reads `view`/`agent` already), no engine change → no verify-score redeploy. Brick 137.

## Phase 13f — Auto-Equip Best (2026-06-12)

170. **A one-click "do the optimal thing" action belongs in the engine, not the UI, the moment the optimum depends on state the UI can only approximate — `equipBest` had to know combat levels, so a UI loop would silently equip inert gear or skip real upgrades.** The follow-up looked like pure UI sugar: a button that fires N `equip` commands. But "best usable per slot" is gated by the player's Attack/Defence levels (a req-14 weapon is inert under level 14), and the canonical level→gear mapping lives in `deriveStats`/`levelsOf` in the engine. A UI-side loop would have had to RE-DERIVE the level gate from the view — duplicating a rule that already exists, and drifting from it the day the xp curve or a `req` moves. Putting `equipBest` in the engine let it reuse the EXACT same best-per-slot scan and first-seen tie-break that `deriveStats` uses, so what the button equips is provably what the combat math will fight with — no second source of truth. Three lessons: (1) the test for "UI convenience vs engine command" isn't how visible the action is, it's whether computing the action's RESULT requires a rule the engine owns — if it does, the convenience is an engine command with a thin button, not UI logic. (2) Reusing the consumer's own selection logic (same scan, same tie-break) is what makes a bulk action consistent with the per-item path — had I written a fresh "best" heuristic I'd have risked equipBest picking a different piece than deriveStats rewards. (3) The additive-by-override discipline from #169 paid off again for free: because the benchmark never issues `equipBest`, `worn` stays empty for it and all three sanity hashes are byte-identical — a new command + handler + UI button cost zero determinism risk because its identity case (never called) IS the existing behaviour. Replay-affecting (new command) → engine.js rebuilt, redeploy batches with 12b/13d/13e. Jesse-greenlit follow-up to the 13e equipment manager. Brick 136.

## Phase 13e — Equipment Manager (2026-06-12)

169. **An additive feature that LAYERS over a deterministic core can be added to a finished system at near-zero risk — `worn` overrides the pack, and "no equipment" is byte-for-byte the old behaviour.** The user wanted a real OSRS equip system on top of a combat/economy engine with golden-hash gates. The temptation was to REPLACE the pack-based gear model with persistent equipment; that would have touched `deriveStats`, every expedition test, death handling, and the loadout UI — a migration with real regression surface. Instead I made `worn` a per-slot OVERRIDE inside `deriveStats(pack, lvls, worn?)`: when `worn` is absent or empty, the function returns exactly what it did before, so every existing test and — critically — the benchmark are untouched. The proof is the sim hash being **byte-identical across all three sanity seeds** after a feature that added two commands, an agent field, a conservation rule, and a UI panel: because the benchmark never equips, `worn` stays empty for it, and "empty worn" is the identity case. Three lessons: (1) the cheapest way to extend a frozen system is to find the function where the new behaviour is a STRICT SUPERSET of the old, gated by a value that defaults to the old behaviour — additive-by-override beats replace-and-migrate. (2) An unchanged golden hash after a feature is the strongest possible proof of non-interference; design the feature so its identity case IS the existing behaviour and the hash will prove it for free. (3) The same `basis`/ownership thread from 13d recurs: equipped gear is "safe on death" because it lives in `worn`, OUTSIDE the at-risk pack — where state lives decides what happens to it, so put player-protected things in a player-protected bucket. Replay-affecting (new commands + deriveStats) → engine.js rebuilt, redeploy batches with 12b/13d. Jesse-present, user-requested. Brick 135.

## Phase 13d — Clerk Gear-Safety (User Bug Fix) (2026-06-12)

168. **The fix that preserves the invariant is the one that uses a distinction the system ALREADY draws — `basis` separated clerk-stock from player-goods without inventing any new state.** A user reported the autoFlip clerk selling gear they bought to equip (and the satchel "always empty"). ## Phase 13b — Resting-Fill Notification (2026-06-12)

## Phase 12w — New-Daily-Record Celebration (2026-06-12)

161. **To celebrate beating a record you must snapshot the record BEFORE the thing that updates it runs — a live-maxed "best" can't also be the mark you're measuring against.** The daily-best pref (12e) maxes itself every tick, so "did worth pass my best?" is unanswerable from the live pref: by the time worth is a new high, the pref already equals it (they move together). ## Phase 12s — Raid Risk/Reward Totals (2026-06-12)

157. **The honest aggregate is the one summed from data you already trust, not the one reconstructed from a model — raid P&L came straight from the Delve Log's own loot figures, sidestepping the cross-loop attribution trap.** The adventure loop had per-raid history (12i) but no bottom line, while trading had a realized total — an asymmetry worth closing. The tempting version computes "earnings by loop" by splitting the net-worth delta into trading vs raiding, but that's fragile: worth-delta includes unrealized holdings swings and market moves, and raid item-drops get SOLD (so they'd double-count into trading realized). Instead `raidTotals` sums the Delve Log's OWN `lootGp` by outcome — banked = survived loot, lost = death loot — an accurate, self-consistent figure that needs no model of how value flows between loops. (Same family as #151's derive-by-subtraction, opposite move: there the total was trustworthy and a part was expensive, so subtract; here the parts are trustworthy and the "total split" would be lossy, so sum the parts.) ## Phase 12o — Live In-Combat Forecast (2026-06-12)

153. **The same estimate can be "good enough" in one context and dangerously wrong in another — a flee-decision aid has to count the damage a pre-fight estimate can gloss.** 12j's embark forecast ignores dragonfire: it's a rough "should I go here?" read at full hp, and being a bit optimistic is harmless. ## Phase 12n — Flip Consistency + the Engine-Content Blast-Radius Check (2026-06-12)

152. **Before reaching for engine content to escape thinning UI ideas, MEASURE the test blast radius — a one-line data change can cascade-break dozens of deterministic tests, and that's the wrong risk to take unsupervised.** Fourteen UI-only bricks deep, I evaluated adding named elites to the shallow regions (0–3) for gameplay depth. ## Phase 12m — Wealth Composition (2026-06-12)

151. **The number you can't easily reproduce is the one to DERIVE by subtraction — holdings = worth − cash − offers, so the split sums exactly without re-implementing the engine's valuation.** A net-worth breakdown (cash vs buy-order escrow vs goods) tempted a re-derivation of the engine's `netWorth` valuation in the UI, which values held goods by walking the resting bids (a bid-walk I'd have to mirror, with all the drift risk of #148's combat formula). The cleaner move: take the two components I CAN read exactly off the view — cash (`view.gp`) and buy escrow (`Σ remaining×price`) — and compute holdings as the **residual** `total − cash − buyOrders`. The split then sums to `playerWorth` by construction, with zero duplication of the hard part. Generalisable: when decomposing a total whose pieces have unequal computability, derive the EXPENSIVE piece by subtraction from the known total and the cheap pieces — you get exactness for free and dodge the duplication. (Contrast #148, where no total was available to subtract from, so the formula HAD to be mirrored.) Bonus honesty: `netWorth` excludes in-progress expedition loot, so I surfaced that as a separate "at risk in the wild" note rather than fudging it into the total — the breakdown tells the truth about what's banked vs what's still on the table. This was also a deliberate breadth choice: a different LENS (liquidity, whole-worth) over a different SCOPE than 12k's by-item holdings concentration. UI-only, no engine change → no verify-score redeploy. Brick 117.

## Phase 12l — Delve Log "Raid Here Again" (2026-06-12)

150. **Two ways to connect a child component to a parent action — lift its state, or pulse it a nonce — and the nonce wins when the child's state is load-bearing for a flow you don't want to destabilise.** Making Delve Log rows jump to their region needed App to drive ExpeditionPanel's region selection. The "proper" move is lifting `regionId` to App and making it a controlled prop — but that turns a working, e2e-covered expedition flow's region selector into controlled state, and every existing setter (RegionMap clicks, etc.) has to be rewired through the parent. Instead I reused the ticket-prefill pattern already in the codebase: App sends a `{regionId, n}` PULSE, ExpeditionPanel keeps its own `useState` and applies the pulse via a nonce-guarded effect. The cost: the child still owns its state (no single source of truth) — acceptable here because nothing else needs to READ the selection. **Testing footgun worth recording: region NAMES appear in at least four places app-wide (DelvePanel, RegionMap SVG, ConquestPanel, the embark selector), so `getByText(regionName)` cross-matches and throws — I targeted the click via the row's UNIQUE title ("click to raid here again") instead.** Same lesson as #147: in an all-mounted multi-room app, text is rarely a unique handle; reach for a title/role/test-id when surfaces share vocabulary. ## Phase 12j — Embark Combat Forecast (2026-06-12)

148. **When the engine's number is a random roll, the UI's honest forecast is its MEAN — and "estimate" labelling is what makes a duplicated formula acceptable.** The adventure side showed raw danger stats but left "can I win here?" as mental math, while the trading side is densely decision-instrumented. Added an embark forecast: ≈rounds to down the worst foe vs ≈rounds for it to down you, favored/risky. Combat damage is RNG (`max(1, roll[ceil(atk/3)..atk] − floor(def/4))`, quest.ts:394), so there's no single number to read — but its MEAN is the right central estimate for a go/no-go call, and `expectedHit` mirrors that mean. The player-strikes-first rule made the verdict a clean inequality: a tie (kill on the very round you'd fall) is a win, so `favored = roundsToKill <= roundsToFall`. The uncomfortable part worth recording: `expectedHit` **duplicates** engine logic in the UI, because the engine's `damage()` is local, unexported, and rng-shaped — there's no mean to import without an engine change (which I'm avoiding to keep bricks redeploy-free). ## Phase 12h — Break-Even Sell Hint (2026-06-12)

146. **`avgCost / (1 - taxRate)` is the right intuition and the wrong number — integer floor-tax means the clean formula overshoots, so the break-even floor has to be searched, not divided.** Completing the ticket's pre-trade instrumentation (12d gave the buy side an average-down preview; the sell side had nothing), I added a break-even floor: the least sell price that recovers your cost after the 2% tax. The naive `avgCost / 0.98` gives 103 for an avg of 100 — but the GE tax is `floor(price * 0.02)`, so 102 already clears (102 − floor(2.04)=2 → 100 = cost exactly). `breakEvenSell` uses the ceil of the clean formula as an UPPER bound, then tightens DOWN to the true least integer where `price − floor(price*taxRate) >= avgCost`. The lesson generalises: whenever a domain rounds with `floor`/`ceil` at integer granularity (gp, ticks, shares), the continuous closed-form is only an estimate — the exact answer lives within ±1 and has to be nailed by a tiny bounded search. I pinned it with a **property test** rather than just example values: for several costs, assert the returned price recovers cost AND one gp under does not — which catches an off-by-one in either tightening loop that hand-picked examples might miss. Players sell just above their average and lose money to the tax constantly; this line makes the real "sell above this to profit" explicit. UI-only, no engine change → no verify-score redeploy. Brick 112.

## Phase 11b — Profit by Item (2026-06-11)

114. **The trading game tracked every fill but never told you which trades actually MADE money — realized P&L is the obvious analytic that was missing.** TopFlips says "what to do next"; nothing said "what worked". `realizedPnL(fills, taxRate)` FIFO-matches each sell against the player's earlier buys in the rolling fill window, nets the sell tax, and reports profit per item — the reflective half of the trading loop. FIFO is the right cost-basis model precisely because fills arrive in tick order, so the buy queue is naturally first-in-first-out with no sorting; a sell walks the queue, splitting partial lots (5@100 + 3@200 against an 8-unit sell), and the per-unit `proceeds = price - floor(price*tax)` mirrors how the ticket already shows flip margin so the numbers reconcile. Two exclusions keep it honest, both tested: an OPEN position (bought, never sold) has no realized profit yet, and a sell with NO in-window cost basis (the matching buy aged out of the 50-fill cap) can't be scored — both contribute zero `soldUnits` and drop out, so the panel never invents a cost basis it doesn't have. The honest caveat is baked into the framing ("recent", window-bounded) rather than pretending to be lifetime P&L. Also the brick where I finally chased down the engine-content blocker properly: the verifier (`supabase/functions/verify-score/index.ts`) takes only `{handle, seed, log}` — NO claimed-hash check — so an engine change doesn't hard-reject submissions, it just leaves the deployed verifier scoring with a stale `engine.js` until `supabase functions deploy` re-runs; and the engine tests are self-consistent (compare two runs) not golden-hash, so they won't break on additive content. Conclusion stands though: shipping replay-affecting code to *main* without the coupled redeploy is an outward-facing live-leaderboard inconsistency I shouldn't introduce on an autonomous firing — so engine content waits for Jesse, and this brick stayed UI-only.

## Phase 10y — Compact Big Numbers (2026-06-11)

111. **Compact notation needs a *principle* for where it applies, or it just trades one illegibility for another.** As wealth compounds, "1,234,567 net · +45,678 gp/min" stops being scannable — but blindly compacting everything would hide digits a trader actually needs (a bid of "1.2K" is useless when you're undercutting by 1). ## Phase 10s — Daily Streak (2026-06-11)

105. **The retention loop is a pure function plus a flame — keep the clock out of the logic and the test trivializes.** A daily streak (Wordle's hook) is conceptually "consecutive days played", but the actual difficulty is the day-gap arithmetic: YYYYMMDD seeds aren't subtractable (20260601 − 20260531 = 70, not 1). Pushing both endpoints through `Date.UTC(y, m-1, d)` and diffing epoch-ms makes month/year rollover correct for free, and — critically — `bumpStreak(prev, today)` takes `today` as an argument rather than reading the clock, so it's a pure reducer: same-day is idempotent (returns the SAME ref so the caller skips the localStorage write), next-day is +1, any gap resets to 1 while preserving `best`. Six one-line assertions cover the whole truth table (fresh / same-day / consecutive / month-roll / year-roll / skip / backwards) with no mocking, no fake timers. The React side is then trivial: one effect keyed on `world.seed` that calls bumpStreak when the active world is the daily — idempotency means "fire on every seed change" is safe, it advances at most once per UTC day. Lesson: when a feature *sounds* like it needs the clock, see if the clock-read can be lifted to the boundary (the effect) and the logic kept pure — the calendar correctness and the test simplicity both fall out. Same shape as the engine's own purity rule, applied to a UI nicety.

## Phase 9r — CSS transform clobbered the SVG transform (2026-06-11, Jesse-reported)

78. **A CSS `transform` (even from a keyframe) fully replaces an element's SVG `transform` attribute — they don't compose.** Jesse's screenshot caught the monster rendered as a clipped blob in the scene's top-left corner instead of on the right. Cause: 9l positioned the monster with `transform="translate(160 52) scale(1)"` (an SVG attribute) AND animated it with a CSS `monster-bob` keyframe that sets `transform: translateY(...)`. CSS transforms win over the presentation attribute, so at every keyframe the positioning translate was discarded and the group fell to (0,0) — an ellipse centered at the origin shows only its lower-right quadrant = the corner blob. Fix: nest — OUTER `<g>` carries the positioning attribute, INNER `<g className="monster">` carries the CSS bob, so the bob composes within the placed frame. Lesson: never put a CSS transform/animation on the same SVG node as a positioning `transform` attribute; separate them across nested groups. The 9l combat-scene test asserted aria-label + splat but not POSITION — strengthened to assert the monster's parent group keeps its `translate(160` so this can't regress. Visual bugs need visual (or structural) assertions; a test that only checks "it rendered" misses "it rendered in the wrong place."

## Phase 9q — Quarantine the Corrupt Save (2026-06-11)

77. **"Recovers from a bad save" and "doesn't destroy a bad save" are different guarantees — we had the first, not the second.** loadGame already caught JSON.parse errors and started fresh, but (a) it skipped the shape gate importSaveString had, so a parseable-but-wrong object normalized into a half-baked Game that crashed later in render, and (b) on any failure the fresh game's first autosave silently OVERWROTE the unreadable original — permanent data loss with no trace. Fix: apply the same world+playerId shape gate, and on any failure QUARANTINE the raw save to `<key>-corrupt` before returning null, so a future-version/foreign/corrupt save is recoverable (export/import) instead of obliterated. The lesson is that graceful-degradation has two halves and tests should assert both: not just "starts fresh on garbage" but "the garbage is still there afterward." Pairs with the 9o boundary: boundary catches render crashes, this catches boot-time save failures — together the game can't be bricked by its own persisted state.

75. **A determinism-pure engine makes crash recovery trivially safe.** Until now a single render throw white-screened the whole live game — and the risk is real and growing: monsterById throws on an unknown id, so a long-lived save crossing a future catalog change could brick the UI. An app-level React error boundary catches render/lifecycle throws, shows a recovery card (reload + copy-save-to-clipboard lifeboat), and — the key property — needs to do NOTHING to protect progress, because the world only mutates through saved commands and the autosave on disk is already the source of truth. The boundary just reads the save string; it never touches the world. Honest scope note: error boundaries catch render-path crashes only, NOT throws inside event handlers (applyCommand in an onClick) — but the render path (CombatScene/RegionMap/monsterById-during-render) was the white-screen risk, and a handler throw leaves the UI standing. Robustness here was cheap precisely because the architecture already separated "what's true" (the saved command log) from "what's drawn."

## Phase 9n — First Real Icons (original) (2026-06-11)

## Phase 9m — The Art Pipeline (2026-06-11, Jesse-directed)

## Phase 8l — Wounds Are Real (2026-06-11)

46. **One mechanic closed both the exploit AND the parity gap — nerf numbers never entered it.** Persistent hp (wounds carry between expeditions, death leaves 1 hp, +1 hp per 3 out-of-field ticks) was aimed at the extract→re-embark free-heal loop, but the rest-threshold sweep (15/25/35/50 across 5 seeds) showed it also resolved FINDINGS #45's queued loot-parity problem: naked grinding fell from **+7.4k–12.7k to +0.3k–3.9k** per sprint — into trading's band, no longer dominant — because the fists-first grinder's whole margin WAS the free heal (take damage for free loot, reset, repeat). Best surviving policy is "dive hurt at 15hp," i.e. risk-taking, which is the right thing to reward. The design lesson: when a strategy dominates, look for the resource it isn't paying for (here: hp) before touching payout numbers — pricing the resource fixes every strategy that leans on it at once, while a loot nerf would have punished geared raiders too. Implementation niceties that kept it cheap: absent-field-=-full-hp means never-wounded saves stay byte-identical (NPC-only sims unaffected, zero gate churn), and full recovery deletes the field to restore canonical form. Geared-grind yield is the missing datum before any further tuning — gear investment (market → expedition capital loop) should now be the best raiding strategy, which is the intended economy.
