## Phase 12a — Sell-Above (Take-Profit) Alerts (2026-06-11)

139. **A price-alert system that only fires on the way DOWN is half a trade — "tell me when to buy" needs its mirror "tell me when to sell".** The watchlist had `≤` buy-below alerts (9w) but nothing for the exit, so a player accumulating a position had no way to be pinged at their take-profit. Added `≥` sell-above alerts as a deliberate MIRROR, not a rewrite: a separate `ew-sell-alerts` pref + a separate `sellFired` re-arm latch + a second firing loop, leaving the proven buy path byte-for-byte untouched (the lowest-risk way to extend a working feature is to parallel it, not refactor it). The one piece worth unifying was the threshold test — `alertHit(last, threshold, dir)` (`below` = `≤`, `above` = `≥`) — so both directions, the App firing loops, and the watchlist's 🔔 indicator share ONE definition of "hit" and can't drift. Both `100 ≤ 100` and `100 ≥ 100` fire (at-threshold counts), pinned by the truth table. Added `aria-label`s to the two number inputs while there (a free a11y win — "buy-below alert for Shark" vs an unlabelled spinner). Mirror tested the same way the buy alert was (sell threshold 1 → always-met → 🔔 row). The alert system is now symmetric: enter and exit, both pinged. Brick 105.

## Phase 11y — Contract Premium & Ready Flag (2026-06-11)

137. **A panel that promises "15–35% over market" but shows only the gross gp forces the player to do the arithmetic the UI already has the inputs for.** The Quartermaster board listed each contract's `qty × unitPrice = total gp` and a deliver button, but not the one number that decides *which* contract is worth chasing: how much it beats just selling on the GE. `contractPremium(unitPrice, marketPrice)` = `(unitPrice − market) / market` surfaces "+22%" per row (green), so a 35%-over deal visibly outranks a 15% one — the Quartermaster's version of the flip-margin/value-band that trading already had. Crucially it can go NEGATIVE: if the market spiked above the agreed price since the contract posted, delivering is now a worse deal than selling, and the red "−8%" says so honestly (the generic "15–35%" copy never could). Also flagged fillable contracts (✓ + faint-green row) since "can I deliver this right now?" is the other half of the decision and the disabled-button state alone is easy to miss. Same shape as every recent surfacing brick: the market price and your inventory were both already in the view; the value was one subtraction and one comparison away. First touch of the contracts surface — fresh area, same lesson. Brick 103.

## Phase 11x — Away-Bar Rate & Compaction (2026-06-11)

136. **The offline summary's total answers "how much" but the idle player's real question is "is my setup WORKING" — and that's a rate, not a sum.** The away-bar (seen on every return) showed the cumulative worth delta, but a +2,400,000 after 20 hours and a +2,400,000 after 20 minutes mean opposite things about your automation. `offlineRatePerMin(delta, ticks)` (1 offline tick ≡ 1 second, so ticks/60 = minutes) turns the gulf into "≈2K/min" — the figure that says whether the clerk/sellsword is actually productive. Shown only when `delta > 0` (a loss has no meaningful "earning rate"), and `fmtCompact` finally landed here (long-queued) so a 28-hour haul reads "+2.4M" not a wall of digits, with the exact value in the title. The rate computation is a one-liner but extracted to a pure helper precisely because the away-bar's own render is hard to test deterministically (offline accrual depends on the sim), so the logic gets a clean truth-table test (60k/10min → 6k/min, losses negative, zero-ticks → 0) while the wiring rides the existing away-banner render test. Pattern: when a UI value's *display path* is non-deterministic to test, pull the *computation* into a pure function and test that — the render only needs to prove it doesn't crash. Brick 102.

## Phase 11w — Worth ETA Projection (2026-06-11)

135. **An idle game's most motivating number is the one that doesn't exist yet — "≈16m to 2M" turns a flat rate into a countdown.** The chart showed where your worth has been (curve) and how fast it's moving (gp/min, 10x), but not the forward question every idle player asks: *when do I hit the next big number?* `nextRoundTarget(n)` picks the next 1/2/5×10^k above current worth (55k→100k, 1.2M→2M, 6M→10M — the "nice" thresholds people actually chase), and the ETA is just `(target − worth) / perMin`. The whole thing is self-contained in WorthChart because the chart already holds `history`, and `worthRate(history)` + last-worth derive both inputs — no new prop, the projection materialized from data the panel already had (the recurring session theme, one more time). Two honesty guards: shown ONLY when `perMin > 0` (no projecting a target you're drifting away from — a negative or flat rate gives no countdown), and the 1/2/5 ladder means the target is always a number a human recognizes as a goal, not an arbitrary "+10%". Reused `fmtDuration` (minutes→"16m"/"2h") and `fmtCompact` (target→"2M") so it speaks the UI's existing vocabulary. Brick 101. Tested the ladder exactly (150k→200k, not 150k→151k) and the end-to-end render (5k/min from 150k → "≈10m to 200K").

## Phase 11v — Getting Started checklist (2026-06-11)

134. **A complex game's onboarding gap isn't a tutorial — it's the absence of a PROSPECTIVE list, and the data to self-check it already exists.** The Deeds panel (and 11s/11t) is retrospective: it celebrates what you've done. A new player drowning in a dense terminal needs the opposite — "what do I do next?" — which a 12-bullet help overlay (read once, forgotten) doesn't provide. `firstSteps(game, view)` is four concrete actions (trade / hire a clerk / fell a monster / reach the sprint horizon), each with a `done` boolean derived from the SAME state the rest of the UI reads (`fills.length`, `view.upgrades.autoFlip`, `stats.monstersSlain`, `world.tick`), so the checklist self-ticks as you play with zero new tracking. Two anti-nag rules keep it from outstaying its welcome: it auto-hides the instant all four are done (a veteran never sees it), and a persisted dismiss (`usePref`) lets the impatient kill it early. Tested the all-done path through the REAL command (`applyCommand buyUpgrade autoFlip`) rather than poking `agent.upgrades`, so the test proves `playerView` actually surfaces a bought clerk — the same end-to-end the player walks. Placed it as the first panel in the Exchange room (where you land), not a modal, so it's reference-not-interruption. Brick 100; FINDINGS hits #134 — a session-long lesson that the highest-leverage UI is almost always *surfacing state the architecture already holds*, whether that's P&L, danger, deeds, or "you're new here, start with this".

## Phase 11u — One-Click Sell Your Position (2026-06-11)

133. **The right place for a one-click action is wherever the state it needs already lives — the position line owns nothing it had to ask App for.** TopFlips' one-click buy (11d) had to thread a buy price up through a callback because the trigger (a flips row) lives outside the ticket and the prefill machinery bridges that gap. The mirror action — one-click sell your whole holding — turned out far simpler because the cost-basis line (11i) is *inside* `TradeTicket`, which already owns `side`/`price`/`qty` state AND has `market` + `position` in scope. So the "sell N" chip just calls `setSide('sell'); setPrice(ask−1); setQty(units)` directly — no prefill nonce, no App prop, no callback. Lesson: before reaching for the cross-component plumbing pattern, check whether the action's origin already sits next to its inputs; internal triggers set state, only external ones need the bridge. Completes the round-trip symmetry (one-click buy a flip ↔ one-click sell a holding) that the trader was missing on the exit side. Button labelled "sell {units}" not "sell" specifically so `getByText('sell')` still resolves to the side toggle alone (locator-collision care, #59 again). Also quietly fixed the position tooltip's stale "(recent fills)" — it's been lifetime since the 11o book. Live on main; PR #1 content batch parked.

## Phase 11t — Deed Markers on the Fortune Curve (2026-06-11)

132. **Two features built one brick apart compose into a third for free — the achievement ticks (11s) had no home until the chart could place them.** Recording milestone ticks last brick was useful on its own ("🏅 latest · 10m ago"), but it also made *this* possible: marking each earned deed as a dot on the Fortune curve, at the exact (tick, worth) where you crossed it — so you see "I hit Dragon Slayer right as my wealth spiked". ## Phase 11p — Trading Scorecard (2026-06-11)

128. **Once the lifetime book existed, the bottom line was two sums away — realized (locked in) + unrealized (paper) is the scorecard the per-item rows never added up.** ProfitPanel listed per-item realized P&L but never totalled it, and said nothing about open positions' paper gains. `totalRealized(book)` sums `book.realized.profit`; `totalUnrealized(book, priceOf)` marks every open lot at the current price — `(price − cost) × qty`. The split mirrors a real brokerage: realized is money you actually banked (tax already netted in the book), unrealized is what the market says your holdings are worth *right now* and evaporates if prices move. Injecting `priceOf` as a function kept `totalUnrealized` pure and testable (mark a@130 → +180, b@40 → −50, net +130) without coupling to the view; the component supplies `view.markets` lastPrice, the test supplies a literal map. The header now reads "realized +X · paper +Y", shown only when either is non-zero so a fresh account stays clean. One test-collision to mind: the realized *total* and a lone item *row* can both render the same "+180", so `getByText('+180')` becomes ambiguous — switched to `getAllByText(...).length > 0`, the same lesson as #59 (exact-text locators collide when a value appears twice). Completes the P&L arc (11b realized rows → 11i cost basis → 11o lifetime book → 11p scorecard): the trader now sees every layer from a single flip's margin up to their whole-run bottom line.

## Phase 11o — Lifetime Trade Book (2026-06-11)

127. **Reimplement-as-wrapper turns a refactor's existing tests into a correctness proof for the new core.** The P&L was window-bound: `realizedPnL`/`openPosition` recomputed FIFO over the capped 50-fill array each render, so an active trader's early flips fell off and "realized profit" silently shrank. The fix is a persistent `TradeBook` (FIFO lots + realized-per-item) accrued ONE fill at a time in `recordFills` — so it survives the window, pinned by a test that buries a +96 gold flip under 60 filler fills and shows it still remembered. The refactor's safety came from making `applyFillToBook` the single FIFO truth and then *reimplementing* the old `realizedPnL`/`openPosition` as one-line wrappers (`realizedFromBook(bookFromFills(fills, tax))`) — their existing truth-table tests (the clean round-trip, the FIFO-across-lots loss leg, the open/orphan exclusions) now re-run against the NEW core and would fail loudly on any divergence; they passed, so the new book provably matches the proven window math. Migration was the only genuinely new risk: old saves have no book, so `normalizeGame` rebuilds it from whatever fills survived (recent only — lost history can't be reconstructed, but it seeds correctly forward), tested by deleting `tradeBook` from a save and asserting the rebuild. Two boundary subtleties: `applyFillToBook`'s once-only accrual rides the *same* dedupe guard that gates `fills.push` (so each fill books exactly once), and `openPosition`'s wrapper passes tax 0 because open lots are tax-independent (tax only touches realized profit, never lot quantities). UI-only — the book lives on `Game`, not `WorldState`, so determinism/replay are untouched. ProfitPanel + the ticket cost basis now read lifetime; "recent" is gone.

## Phase 11n — Per-Axis Danger Colour (2026-06-11)

126. **Colour the FACTS per axis and you get a survival cue without a survival verdict — "their ⚔ beats your 🛡" is true; "you'll die here" is a guess.** 11l/11m put both sides' stats on the embark screen; the visual completion is colouring the foe's numbers relative to yours. The trap I kept dodging (a green/red "ready?" badge) needs a survivability model — hp, food, dragonfire, leech, play all matter — and would lie. But colouring each foe stat *independently* against the matching player stat is pure fact: the foe's ⚔ goes red exactly when `foe.atk > your def` (their hits land through your armour), the foe's 🛡 goes red exactly when `foe.def ≥ your atk` (your hits barely dent). A fresh player at Lumbridge sees ⚔4 RED (a goblin really can hit your def-2 body) but 🛡1 GREEN (your atk-5 shreds it) — both true, and together they tell the real story (you win, but you'll take chip damage) without claiming an outcome. The per-axis split is what keeps it honest: a single combined verdict would have to weigh offence against defence and that weighting is the guess. Reused `deriveStats` (11m) for the player side and `regionDanger` (11l) for the foe side — the cue is just two comparisons over numbers already computed. Test pins the exact case (PLAYER_BASE atk5/def2 → ⚔4 down, 🛡1 up at Lumbridge), which doubles as documentation of the colour rule. Live on main; PR #1 (Forge+Skarn+Altar) still parked.

## Phase 11l — Region Danger Readout (2026-06-11)

124. **An honest factual readout beats a fragile verdict — show the foe's stats, let the player judge against their own.** Picking a region to raid, the player had the flavor text and the unlock gate but no sense of *how hard it hits*. ## Phase 11i — Open-Position Cost Basis (2026-06-11)

121. **The realized panel said what flips you finished; the missing half is whether you're up on what you still HOLD — same FIFO idea, the leftover lots instead of the matched ones.** ProfitPanel (11b) reports completed round-trips; nothing showed unrealized P&L on open positions. `openPosition(fills, itemId)` runs the identical FIFO match but reads the *opposite* output: after sells consume buys, the *remaining* buy lots ARE what you bought and still hold, and their quantity-weighted average is your cost basis. The ticket shows "position: N @ avg X · ±Y% now" for the selected item — compare avgCost to lastPrice and you see the unrealized gain before you ever sell. Two honesty boundaries, both tested: loot has no buy fill so it contributes no basis (a sell with no prior buy is just dropped — you can't have negative held), and like realizedPnL it's window-bounded, so the label is deliberately "cost basis (recent fills)", not all-time. Chose this additive ticket signal over the bigger persistent-lifetime-P&L rewrite (still queued) precisely because it needed ZERO save-format change — `openPosition` is a pure read over the existing fills, passed as one prop. Render test seeds `game.fills` with a single buy and asserts the line renders for the default-selected item; the `getNodeText` quirk (direct text nodes only) means `getByText(/@ avg 100/)` matches the `<p>` even though the unit count sits in a nested `<b>`. Realized (done) + unrealized (holding) now complete the trader's P&L picture.

## Phase 11f — Order-Book Liquidity Bar (2026-06-11)

118. **Surfacing a signal the BOTS already trade on levels the field between player and AI — and it was one derived view field away.** (#117 is the Field Forge, on branch `feat/forge-event`/PR #1 awaiting a coupled verify-score redeploy — numbered there.) ## Phase 11d — One-Click Flip (2026-06-11)

116. **Make the informational panel operational by threading one number through the callback — and you get composition coverage for free.** TopFlips told you the best flip and its buy price, but clicking only *selected* the item; the player still had to set side=buy and retype bid+1. Deliberately did NOT prefill a quantity: `TicketPrefill` is `{side, price}` and the player's size depends on capital/limit/appetite, so auto-filling qty would be presumptuous where price is just the obvious mechanical default. ## Phase 11c — Flip Efficiency & Limit (2026-06-11)

115. **When a "better" metric needs a model you can't verify, show the honest metrics and let the player rank — don't launder a guess into the sort order.** The queued idea was to rank TopFlips by *realizable* profit (margin × units you can actually move). But "units you can move" depends on order flow the UI can't see — `bidDepth`/`askDepth` are resting liquidity, not future fills — so any realizable-units number would be a guess presented as fact, and re-sorting on it would make the ranking *less* trustworthy, not more. So the ranking stayed on absolute margin (well-defined) and instead each row gained two metrics that ARE well-defined from data already in `MarketView`: return-on-cost (`margin/buy` — efficiency, so a +20 on a 100gp item reads as 20% vs +180 on 5000gp reading 3.6%) and the GE buy limit (`buyRemaining`, previously ticket-only — which flips are size-capped). Both are facts, not forecasts. Additive-field discipline paid off: extending `FlipPick` with `roi`/`limit` didn't break the existing rankFlips tests because they used `toMatchObject`/`length`/`map`, never `toEqual` on the whole object — the looseness that bit me in #111 (a too-loose assertion surviving) is the same looseness that makes additive change safe here. Render-test footgun re-confirmed: testing-library's `getNodeText` reads only an element's *direct* text nodes, so a margin span "+77" with a nested `<span>7.7%</span>` child still matches `getByText('+77')` (the child's "7.7%" is invisible to the parent match) — which is exactly why the pre-existing "+77" assertion kept passing after I nested the ROI inside it.

## Phase 11b — Profit by Item (2026-06-11)

114. **The trading game tracked every fill but never told you which trades actually MADE money — realized P&L is the obvious analytic that was missing.** TopFlips says "what to do next"; nothing said "what worked". `realizedPnL(fills, taxRate)` FIFO-matches each sell against the player's earlier buys in the rolling fill window, nets the sell tax, and reports profit per item — the reflective half of the trading loop. FIFO is the right cost-basis model precisely because fills arrive in tick order, so the buy queue is naturally first-in-first-out with no sorting; a sell walks the queue, splitting partial lots (5@100 + 3@200 against an 8-unit sell), and the per-unit `proceeds = price - floor(price*tax)` mirrors how the ticket already shows flip margin so the numbers reconcile. Two exclusions keep it honest, both tested: an OPEN position (bought, never sold) has no realized profit yet, and a sell with NO in-window cost basis (the matching buy aged out of the 50-fill cap) can't be scored — both contribute zero `soldUnits` and drop out, so the panel never invents a cost basis it doesn't have. The honest caveat is baked into the framing ("recent", window-bounded) rather than pretending to be lifetime P&L. Also the brick where I finally chased down the engine-content blocker properly: the verifier (`supabase/functions/verify-score/index.ts`) takes only `{handle, seed, log}` — NO claimed-hash check — so an engine change doesn't hard-reject submissions, it just leaves the deployed verifier scoring with a stale `engine.js` until `supabase functions deploy` re-runs; and the engine tests are self-consistent (compare two runs) not golden-hash, so they won't break on additive content. Conclusion stands though: shipping replay-affecting code to *main* without the coupled redeploy is an outward-facing live-leaderboard inconsistency I shouldn't introduce on an autonomous firing — so engine content waits for Jesse, and this brick stayed UI-only.

## Phase 10y — Compact Big Numbers (2026-06-11)

111. **Compact notation needs a *principle* for where it applies, or it just trades one illegibility for another.** As wealth compounds, "1,234,567 net · +45,678 gp/min" stops being scannable — but blindly compacting everything would hide digits a trader actually needs (a bid of "1.2K" is useless when you're undercutting by 1). The principle that scoped the brick: **compact the approximate aggregates, keep the exact figures exact.** Net worth (a liquidation *estimate*), the all-time delta, and the earning *rate* are inherently fuzzy → `fmtCompact` (12.3K / 1.23M / 1.5B). Cash gp, prices, and order quantities are things you transact on → untouched. Every compacted figure carries the full value in its `title`, so precision is one hover away. Implementation leaned on the platform instead of hand-rolling unit thresholds: `Intl.NumberFormat({notation:'compact', maximumSignificantDigits:3})` handles all the rounding/boundary cases (999,999 → "1M") that a hand-rolled `/1e6` would fumble; the only custom rule is "<10k stays exact-with-commas" because compacting "9,999" to "10.0K" loses more than it saves. Caught a latent test coupling by reading first: a test asserted `getAllByText('55,000').length > 0` with a "(gp + net)" comment expecting BOTH to render the comma string — after the split, net became "55K" so only gp matches, but `> 0` still holds (the assertion was looser than its comment, so it survived; had it been `=== 2` it would have broken). The `+0` fresh-delta test also survived because `fmtCompact(0)` is exact "0". Lesson banked: when changing a display format, grep the tests for the *old* string, not just the component.

## Phase 10x — Earning-Rate Cue (2026-06-11)

110. **The cumulative net delta answers "have I won?"; an idle game also needs "am I winning *now*?" — and the data for it was already on disk.** The masthead showed net worth and the all-time delta vs start, but that delta is dominated by long-ago gains: a player whose setup has gone net-negative for the last hour still sees a big green "+250,000" and no signal that they're now bleeding. `worthRate(history, windowTicks=600)` takes the slope of the most recent ~10 min of the *throttled worth samples the Fortune chart already persists* (50-tick cadence, 240 cap) and reports gp/min (60 ticks = 1 min, matching fmtDuration's vocabulary). The windowing is the subtle part: walk back from the newest sample collecting only those within `windowTicks`, so old history can't drag the slope — pinned by a test where a tick-0 sample sits outside a 600-window ending at 1000 and is correctly ignored (slope measured over the 500-tick span, not 1000). Two honest-null guards: <2 samples, or a window so tight only the last sample falls inside it (dt 0) → no fictional rate. Cost was one pure function + one masthead span; zero new state, zero engine touch, because the time series was a byproduct of the chart feature built long ago. Recurring theme this whole session (#107/#108/#109): the high-value signal is usually *latent in state already computed* — the brick is making it visible, not generating it. Placed beside the delta with up/down colour so the two reads sit together: lifetime result + current trajectory.

## Phase 10t — Streak-at-Risk Nudge (2026-06-11)

106. **A retention reward shown only to people already retained is backwards — the FOMO trigger has to fire where the lapse happens.** 10s's 🔥 ember only rendered while you were *on* the daily, i.e. it congratulated players who'd already returned and said nothing to the ones drifting away — exactly inverted from how a streak drives behaviour. ## Phase 10s — Daily Streak (2026-06-11)

105. **The retention loop is a pure function plus a flame — keep the clock out of the logic and the test trivializes.** A daily streak (Wordle's hook) is conceptually "consecutive days played", but the actual difficulty is the day-gap arithmetic: YYYYMMDD seeds aren't subtractable (20260601 − 20260531 = 70, not 1). Pushing both endpoints through `Date.UTC(y, m-1, d)` and diffing epoch-ms makes month/year rollover correct for free, and — critically — `bumpStreak(prev, today)` takes `today` as an argument rather than reading the clock, so it's a pure reducer: same-day is idempotent (returns the SAME ref so the caller skips the localStorage write), next-day is +1, any gap resets to 1 while preserving `best`. Six one-line assertions cover the whole truth table (fresh / same-day / consecutive / month-roll / year-roll / skip / backwards) with no mocking, no fake timers. The React side is then trivial: one effect keyed on `world.seed` that calls bumpStreak when the active world is the daily — idempotency means "fire on every seed change" is safe, it advances at most once per UTC day. Lesson: when a feature *sounds* like it needs the clock, see if the clock-read can be lifted to the boundary (the effect) and the logic kept pure — the calendar correctness and the test simplicity both fall out. Same shape as the engine's own purity rule, applied to a UI nicety.

## Phase 9r — CSS transform clobbered the SVG transform (2026-06-11, Jesse-reported)

78. **A CSS `transform` (even from a keyframe) fully replaces an element's SVG `transform` attribute — they don't compose.** Jesse's screenshot caught the monster rendered as a clipped blob in the scene's top-left corner instead of on the right. Cause: 9l positioned the monster with `transform="translate(160 52) scale(1)"` (an SVG attribute) AND animated it with a CSS `monster-bob` keyframe that sets `transform: translateY(...)`. CSS transforms win over the presentation attribute, so at every keyframe the positioning translate was discarded and the group fell to (0,0) — an ellipse centered at the origin shows only its lower-right quadrant = the corner blob. Fix: nest — OUTER `<g>` carries the positioning attribute, INNER `<g className="monster">` carries the CSS bob, so the bob composes within the placed frame. Lesson: never put a CSS transform/animation on the same SVG node as a positioning `transform` attribute; separate them across nested groups. The 9l combat-scene test asserted aria-label + splat but not POSITION — strengthened to assert the monster's parent group keeps its `translate(160` so this can't regress. Visual bugs need visual (or structural) assertions; a test that only checks "it rendered" misses "it rendered in the wrong place."

## Phase 9q — Quarantine the Corrupt Save (2026-06-11)

77. **"Recovers from a bad save" and "doesn't destroy a bad save" are different guarantees — we had the first, not the second.** loadGame already caught JSON.parse errors and started fresh, but (a) it skipped the shape gate importSaveString had, so a parseable-but-wrong object normalized into a half-baked Game that crashed later in render, and (b) on any failure the fresh game's first autosave silently OVERWROTE the unreadable original — permanent data loss with no trace. Fix: apply the same world+playerId shape gate, and on any failure QUARANTINE the raw save to `<key>-corrupt` before returning null, so a future-version/foreign/corrupt save is recoverable (export/import) instead of obliterated. The lesson is that graceful-degradation has two halves and tests should assert both: not just "starts fresh on garbage" but "the garbage is still there afterward." Pairs with the 9o boundary: boundary catches render crashes, this catches boot-time save failures — together the game can't be bricked by its own persisted state.
